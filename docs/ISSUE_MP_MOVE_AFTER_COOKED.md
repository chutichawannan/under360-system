# 🍳 ISSUE: เลื่อนวันส่ง Meal Plan แล้ว "ได้เมนูเดิมหรือเปล่า" — ขึ้นกับว่าครัวทำไปหรือยัง

> **นัทตั้งโจทย์เอง 17 ส.ค. 2569:** *"ลูกค้าเลื่อนวันส่งในมีลแพลน ก็ต้องเช็คกันอีกว่าเลื่อนวันแล้วทำไปหรือยัง ... เลื่อนวันแล้วจะได้เมนูเดิมหรือไม่ได้ของเดิม ขึ้นอยู่กับว่าทำไปหรือยัง"*
>
> คู่กับ [`ISSUE_MP_ROUND_SHIFT.md`](ISSUE_MP_ROUND_SHIFT.md) (เลื่อนแล้วรอบไปทับกัน) — คนละปัญหา แต่เกิดจากปุ่มเดียวกัน

---

## 🔴 ปัญหาแรกสุด: **ระบบตอบไม่ได้เลยว่า "ทำไปหรือยัง"**

`mp_deliveries.status` ที่มีอยู่จริงทั้งตาราง (1,786 แถว):

| status | จำนวน | แปลว่า |
|---|---|---|
| `scheduled` | 53 | จองรอบไว้ ยังไม่จ่ายเมนู |
| `menu_assigned` | 50 | แอดมินจ่ายเมนูแล้ว |
| `delivered` | 1,669 | **ส่งถึงมือลูกค้าแล้ว** |
| `cancelled` / `skip_requested` / `no_change` | 14 | — |

**ไม่มีสถานะไหนเลยที่แปลว่า "ครัวทำเสร็จแล้ว แต่ยังไม่ได้ส่ง"**
ช่วงเวลาระหว่าง *ครัวลงมือทำ* → *แมสไปส่ง* ระบบยังขึ้นว่า `menu_assigned` เหมือนตอนยังไม่ได้ทำอะไรเลย

**และตอนนี้ปุ่มเลื่อนวัน (`planMoveRound`) แก้แค่ `delivery_date` — เมนูเดิมตามไปด้วยเสมอ ไม่ว่าจะทำไปแล้วหรือยัง**
→ ถ้าครัวทำเสร็จแล้วลูกค้าเลื่อน = กล่องที่ทำแล้วค้างอยู่ในครัว (ปรุงสด เก็บข้ามวันไม่ได้) แล้ววันใหม่ระบบสั่งให้ทำเมนูเดิมซ้ำอีกรอบ **ไม่มีใครรู้ว่าของหายไปไหน**

---

## 🕐 เส้นแบ่ง "ทำแล้ว / ยังไม่ทำ" — ใช้ของที่มีอยู่แล้วได้เลย ไม่ต้องเพิ่มข้อมูล

ข้อเท็จจริงของ Meal Plan (จาก CLAUDE.md + ที่นัทยืนยันเอง):
- **ปรุงสดเช้าวันส่ง ส่งบ่าย** — ไม่ได้ทำล่วงหน้า
- **ตัดยอดสั่ง 08:30 ของวันส่ง** — เส้นนี้มีอยู่แล้วในระบบ (`MP_CUTOFF_HOUR/MIN`)
- ครัวเข้า 08:00 · ผักมาเกือบ 09:00

👉 **เสนอใช้ 08:30 ของวันส่ง เป็นเส้นแบ่งเดียวกัน** — ไม่ต้องรอครัวกดอะไรเพิ่ม ใช้ได้ตั้งแต่วันแรก

```
เลื่อนก่อน 08:30 ของวันส่งเดิม   → ถือว่า "ยังไม่ได้ทำ"
เลื่อนหลัง 08:30 ของวันส่งเดิม   → ถือว่า "ทำไปแล้ว"
```

⚠️ **ข้อจำกัดที่ต้องรู้:** นี่คือการ *เดาจากเวลา* ไม่ใช่ความจริง — วันที่ครัวทำช้า/ทำไม่ทัน มันจะเดาผิด
→ ถ้าอยากแม่นจริงต้องให้ **ครัวกดปุ่ม "ทำเสร็จแล้ว"** ในหน้าครัว (สถานะใหม่ 1 ตัว) แต่นั่นคือเพิ่มงานให้ครัว
**เสนอ: เริ่มจากเวลา ก่อน → ถ้าเดาผิดบ่อยค่อยเพิ่มปุ่ม**

## 📐 กลไกที่เสนอ

### กรณี A — เลื่อนก่อน 08:30 (ยังไม่ได้ทำ)
**ยกทั้งรอบไปวันใหม่ พร้อมเมนูเดิม** · ไม่มีของเสีย ไม่ต้องจ่ายเมนูใหม่

⚠️ **แต่มีเงื่อนไขซ้อน:** เมนูเดิมอาจ **ไม่อยู่ในแผนผลิตของวันใหม่**
ครัวทำเมนูเป็นชุดต่อวัน — วันจันทร์ทำ 16 เมนู วันพุธเป็นอีกชุดหนึ่ง
→ ถ้าเมนูเดิมไม่อยู่ในชุดของวันใหม่ = **ครัวต้องทำจานเดียวเพื่อคนเดียว** (ต้นทุนพุ่ง เตรียมของไม่คุ้ม)
→ **ระบบต้องเตือนตอนเลื่อน** ว่า "เมนูนี้ไม่อยู่ในแผนวันใหม่ — จะให้จ่ายเมนูใหม่ไหม"

### กรณี B — เลื่อนหลัง 08:30 (ทำไปแล้ว)
**เมนูเดิมไปกับวันใหม่ไม่ได้** — อาหารปรุงสดวันนี้ เก็บไปส่งวันพุธไม่ได้
→ วันใหม่ต้อง **ได้เมนูของวันนั้น** (จ่ายใหม่)
→ แล้ว **กล่องที่ทำไปแล้ววันนี้จะเอาไปไหน** — อันนี้ต้องนัทเคาะ ผมเลือกแทนไม่ได้เพราะเป็นเรื่องเงิน:

| ทางเลือก | ผลกับลูกค้า | ผลกับร้าน |
|---|---|---|
| **B1** ไม่ให้เลื่อน — บอกว่าเลยเวลาแล้ว ส่งวันเดิม | ลูกค้าอาจไม่อยู่รับ ของเสียอยู่ดี | ไม่เสียของในบัญชี แต่เสี่ยงส่งแล้วไม่มีคนรับ |
| **B2** เลื่อนได้ ของวันนี้ทิ้ง ร้านรับภาระ | ลูกค้าแฮปปี้ | **ร้านจ่าย 1 กล่องฟรีทุกครั้ง** |
| **B3** เลื่อนได้ + เอากล่องที่ทำแล้วไปขายเป็นเมนูสต็อค/อาหารพนักงาน | ลูกค้าแฮปปี้ | กู้ต้นทุนคืนได้บางส่วน |

💡 **ผมเอนไปทาง B3** — ตรงกับสมดุลที่นัทเน้นไว้ (ดูแลลูกค้า **และ** ไม่ให้ร้านเจ็บ)
แต่ต้องมีที่ให้ครัวบันทึกว่า "กล่องนี้เหลือ เอาไปขายต่อ/พนักงานกิน" ไม่งั้นของหายเงียบเหมือนเดิม

### กรณี C — เลื่อนไปวันที่ตัวเองมีรอบอยู่แล้ว
ดู [`ISSUE_MP_ROUND_SHIFT.md`](ISSUE_MP_ROUND_SHIFT.md) — ตอนนี้ **ทับกันได้เงียบๆ เกิดไปแล้ว 11 เคส**

## ✅ สิ่งที่ระบบต้องทำเพิ่ม (ถ้านัทเอาตามนี้)

1. **ตอนกดเลื่อน ระบบบอกก่อนว่ากำลังอยู่กรณีไหน** — "ยังไม่ได้ทำ ยกเมนูเดิมไปด้วย" vs "ทำไปแล้ว ต้องจ่ายเมนูใหม่"
2. **กรณี B ล้างเมนูของรอบนั้น** (`menu_items = []` · สถานะกลับเป็น `scheduled`) → รอบใหม่เข้าคิวให้แอดมินจ่ายเมนูใหม่ **ไม่ใช่ลากเมนูเก่าตามไป**
3. **กรณี A เช็คว่าเมนูเดิมอยู่ในแผนวันใหม่ไหม** ถ้าไม่อยู่ ให้เตือน
4. **บันทึกทุกครั้งว่าเลื่อนตอนไหน ก่อนหรือหลังเส้น** ลง `admin_notes` — เดือนหน้าจะได้ตอบได้ว่าเลื่อนหลังครัวทำบ่อยแค่ไหน คุ้มที่จะทำปุ่ม "ทำเสร็จแล้ว" ไหม
5. **(ถ้าเอา B3)** ที่ให้ครัวบันทึกกล่องที่เหลือ
