```

## 🧩 ปัญหาที่นัทไล่มา — **คำต่อคำ ห้ามตีความ ห้ามย่อ**

### ① เลขบนจอกับของในตู้ไม่ตรง
> *"ปัญหาของ S2 และทุกรายการ เกิดขึ้นที่ในระบบของมือถือพนักงานครัว เห็นตอนนี้ว่า**มีจริงทั้งหมด 4 แต่นับในตู้เย็นตอนนี้ดันมี 3**"*

### ② ของ 4 ชิ้นนั้น "ถูกจัดไปแล้ว" — แล้ว 3 ที่เหลือคือของใคร
> *"ไม่ใช่แค่นี้ เพราะว่า**มีจริง 4 และมีรูปหน้าคนทั้งหมด 4** แปลว่านอกจากมีจริงแล้ว รายการนี้**ถูกจัดไปเรียบร้อยแล้ว** ดังนั้นทั้ง 4 รายการนี้ควรจะอยู่ในถุงอาหารที่ถูกแพ็คไว้แล้ว และ**เราไม่รู้ว่าถูกส่งไปหรือยัง หรือยังอยู่ในครัว** และ 3 รายการที่ยังเหลืออยู่ในตู้เย็น **มันควรจะเป็นของ 4 คนนั้น หรือว่ามันเป็นของที่เหลือขึ้นมาจริงๆ**"*

### ③ จะเพิ่มของที่เหลือกลับเข้าระบบยังไง — ตอนนี้ใช้ช่องผิดความหมายอยู่
> *"ปัญหาที่ตามมาก็คือ**เราจะเพิ่มสต๊อกยังไง ช่องไหนดี** ตอนนี้แก้ปัญหาเบื้องต้นโดยการให้โม๋ข่องแจ้งลงไปในระบบว่า**ทำเพิ่ม 3** ซึ่งจริงๆ **เราไม่ได้ทำเพิ่มขึ้นมา 3 หรอก แต่เรามีเหลือ 3** เราเลยใส่เติมเข้าไปว่าทำเพิ่ม 3 ซึ่งเราก็ไม่รู้ว่าจะมีปัญหาตามมาไหม"*

### ④ 3 ที่เหลือ อาจเป็นของที่ยังไม่ได้จัด — แต่ก็ไม่ควรมีของเหลือตอนเช้า
> *"เช่น เอ้ย จริงๆ 3 อันนี้**ควรจะถูกจัดให้ลูกค้าแต่ว่ายังไม่ได้จัด** ซึ่งอันนี้ก็มีความเป็นไปได้ และก็มีความเป็นไปไม่ได้เช่นกัน เพราะว่า**ทุกๆ วันควรจัดของตอนจบวัน** ซึ่งตอนนี้มันเป็น**เริ่มต้นเช้าวันใหม่ ไม่ควรมีของเหลือ 3**"*

### ⑤ ไม่รู้ว่าลูกค้าสั่งตอนไหน สต๊อกถูกตัดเมื่อไหร่
> *"ยังจะมีปัญหาแทรกซ้อนอีกเยอะมาก **ไม่รู้ลูกค้าสั่งตอนไหน ถูกตัดสต๊อกไปเมื่อไหร่** บางทีก็อาจจะมีเหตุการณ์เช่น มีจริง 3 ลูกค้ากดสั่งมาตอนกลางคืนที่ครัวเลิกงาน ก็อาจจะกลายเป็นมีจริง 4 ที่ถูกจัดเข้าไป ทำให้สต๊อกเป็นศูนย์ อันนี้ก็คิดมั่วไปหมด"*

### ⑥ งานจัดของระหว่างวันของกิ๊ฟ
> *"ระหว่างวันกิ๊ฟสั่งให้ครัวจัดของให้ลูกค้า ซึ่งก็ต้องมาดูกันอีกว่า**จัดจากรายการที่ถูกหักสต๊อกไว้แล้ว หรือว่ามีลูกค้ามาสั่งด่วน**"*

## 🗝️ คำตอบจากกิ๊ฟ (แอดมิน) — **นัทถามเองแล้ว · หลักฐานชั้นต้นที่สำคัญที่สุดของ issue นี้**

> *"มีค่ะแต่ไม่บ่อย ส่วนมาก**ที่สต๊อกไม่ตรงเพราะ order ลูกค้าบางคนขาด ก็จะให้ลูกค้าเลือกเมนูใหม่ทดแทน** อาจจะเป็นส่วนที่ทำให้สต๊อกไม่ตรง · **กรณีการตัดสต๊อกของหนูคือตัดแมนนวล โดยเข้าหลังบ้านแล้วลบเอาเลยค่ะ**"*

🔴 **อ่านให้ดี:** มีการเปลี่ยนสต๊อกที่**ไม่ได้ผ่านทางที่ระบบออกแบบไว้** และ**ไม่ได้ผ่านหน้าครัว** — ทุกห้องต้องไล่ว่าการ "ลบเอาเลยที่หลังบ้าน" ไปโผล่/ไม่โผล่ที่ไหนบ้าง

⚠️ **ห้ามตีความว่ากิ๊ฟทำผิด** — กิ๊ฟทำเพราะไม่มีทางอื่นให้ทำ **ที่ผิดคือระบบไม่มีช่องให้** (กฎบ้านนี้: ระบบที่บังคับให้คนเลี่ยง = ระบบออกแบบพลาด)

**ข้อ 2 — ผลพวงที่อันตรายที่สุดของข้อ 1: กิ๊ฟลบใบที่หลังบ้าน แล้ว "มีจริง" ขยับเองทันที ทั้งที่ไม่มีใครแตะสต็อกเลย**

ใครทำให้ขยับ : กิ๊ฟ (โดยไม่รู้ว่าการลบใบไปขยับเลขครัวด้วย) — ⚠️ ไม่ใช่ความผิดกิ๊ฟ ระบบไม่มีช่องอื่นให้
```

**ข้อ 3 — ตอบข้อ 2 ของนัท ("สั่งแล้ว 4 หักออกหรือยัง") : ไม่หักซ้ำ แต่เลขที่จอขึ้นวันนี้ไม่ตรงกับใบจริง**
```
เหตุ     : สั่งแล้ว ถูกหักจาก stock_total ไปแล้วตอนลูกค้ากด · "มีจริง" เอามาบวกกลับ = ไม่ซ้ำ
           แต่เลข "สั่งแล้ว 4" ที่จอขึ้นเช้านี้ ไม่ตรงกับใบจริงในระบบ
หลักฐาน  : query order_items ของ S062 วันส่ง 10 ก.ย. = U-0910-003 x3 ใบเดียว → รวม 3 ไม่ใช่ 4
           (ใบอื่นที่มี S062 เป็นวันส่ง 7/8/11 ก.ย. คนละวัน)
           ⚠️ ส่วนต่าง 1 กล่องนี้ = นิยาม "สั่งแล้ว" ของหน้าครัวกว้างกว่า "วันส่งวันนี้"
             → ฝาก U ยืนยันว่า stkOrderedMap นับใบสถานะไหน/วันไหนบ้าง (รวม cancelled ด้วยไหม)
เกิดตอนไหน : ทุกวัน
ใครทำให้ขยับ : ระบบ (นิยามคนละชุดกับที่คนเข้าใจ)
```

**ข้อ 4 — ตอบข้อ 5 ของนัท ("ใส่ทำเพิ่ม 3 จะพังไหม") : พังแน่ และพังเงียบ**
```
เหตุ     : "กำลังเติม" ค้างข้ามคืน = ระบบสรุปเองว่าทำเสร็จแล้ว แล้วบวกเข้า "มีจริง" ตอนเช้า
           ของเหลือ 3 ที่กรอกเป็น "ทำเพิ่ม 3" จะถูกนับเป็นของใหม่อีก 3 → ของ 3 กลายเป็น 6
หลักฐาน  : kitchen_queue.html ปิดวันอัตโนมัติ -> stkCommit(m, real+inc, 0, "ปิดวันอัตโนมัติ")
           เกิดจริงแล้วกับ S062: 8 ก.ย. 09:02 "มีจริง 2→7 · กำลังเติม 5→0"
           = เช้าวันนั้นระบบเพิ่มของให้ 5 กล่องโดยไม่มีใครทำ
           ของที่โม๋ข่องกรอก "ทำเพิ่ม 3" เมื่อ 10 ก.ย. 10:49 จะโดนแบบเดียวกันพรุ่งนี้เช้า
เกิดตอนไหน : เช้าวันถัดไป
ใครทำให้ขยับ : ระบบเอง
```
🔴 **ถ้าไม่แตะอะไรเลย พรุ่งนี้เช้า S062 จะขึ้น "มีจริง" เกินความจริงอีก 3 กล่อง — เฝ้าดูได้เลย เป็นการทดสอบสมมติฐานนี้ในตัว**

**ข้อ 5 — มีทางที่ 6 ที่ยังไม่มีใครพูดถึง: ตัดสต็อกไม่สำเร็จ แล้วออเดอร์ยังผ่าน (เงียบสนิท)**
```
เหตุ     : ตอนลูกค้ากดสั่ง ระบบเรียก RPC adjust_stock แบบ best-effort
           ตัดไม่สำเร็จ = ไม่ throw ไม่บันทึก ไม่เตือนใคร ออเดอร์บันทึกปกติ
หลักฐาน  : liff_customer.html — คอมเมนต์เขียนเองว่า
             "best-effort: ตัดไม่สำเร็จห้ามทำให้ออเดอร์ลูกค้าพัง — แค่ log ไว้ให้แอดมินเช็ค"
           แต่ที่เขียนจริงคือ console.error (ขึ้นในเบราว์เซอร์ลูกค้าเท่านั้น)

ใครทำให้ขยับ : ไม่มีใคร — นี่คือ "ทางที่เลขไม่ขยับทั้งที่ควรขยับ" = ขายเกินโดยไม่มีใครรู้
```

**แย้ง/เสริมห้องอื่น:**

✅ **เสริมเลขา ข้อ 2 — ช่วงที่ว่า "6→4 ไม่มีแถว log" ผมหาที่มาเจอแล้ว**
U-0910-003 (x3) สั่ง 9 ก.ย. 13:48 + U-0911-012 (x1) สั่ง 9 ก.ย. **23:58** = **4 กล่องถูกตัดในคืนนั้น** พอดีกับที่หายไป
→ **ไม่ใช่เลขหายลอยๆ — มันคือลูกค้ากดสั่งจริง แต่ทางนี้ไม่ลง log เลย** (ยืนยันข้อสรุปของเลขา แต่ตอนนี้มีชื่อใบกำกับแล้ว ตามต่อได้)
และใบ 23:58 = **เคสที่นัทเดาไว้ในข้อ ⑤ เป๊ะ** ("ลูกค้ากดสั่งตอนกลางคืนที่ครัวเลิกงาน") — เกิดจริงแล้ว ไม่ใช่สมมติ

🔻 **เสริมเลขา ข้อ 1 — "≥5 ทาง" ผมว่าต้องแยกเป็น 2 ประเภท ไม่ใช่นับรวม**
| | ทาง | ลง log ไหม |
|---|---|---|
| **ขยับแล้วไม่ทิ้งรอย** | ลูกค้ากดสั่ง · กิ๊ฟลบใบหลังบ้าน · ยกเลิกใบ | ❌ |
| **ขยับแล้วมีรอย** | ครัวกรอก · ปิดวันอัตโนมัติ · แอดมินพิมพ์เลขหน้า DB | ✅ |
| 🔴 **ควรขยับแต่ไม่ขยับ** | ตัดสต็อกล้มเหลว (ข้อ 5) | ❌ และไม่มีใครรู้ |
แถวล่างสุดอันตรายกว่า 2 แถวบน เพราะ **2 แถวบนคือ "ตามไม่เจอ" แต่แถวล่างคือ "ไม่รู้ว่ามีอะไรให้ตาม"**

⚖️ **เรื่องนิยาม — ขอเสนอคำที่ทุกห้องใช้ตรงกันในประชุมนี้ (ไม่ใช่ทางแก้ แค่กันเถียงกันคนละภาษา)**
ตอนนี้คำว่า "มีจริง" ถูกใช้ 2 ความหมายสลับกันในไฟล์นี้ — **"ของในตู้" (ที่นัท/ครัวหมายถึง)** กับ **"เลขที่ระบบคำนวณ" (ที่จอแสดง)**
