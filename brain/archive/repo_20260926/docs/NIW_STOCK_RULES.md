# กติกาสต็อกเมนูประจำสัปดาห์ — นัทเล่าเอง 1 ก.ย. 2026

> ⚠️ **ยังไม่ครบ** — นัทบอกเอง: *"ยังมีกติกาอีกหลายๆอย่างที่ฉันเพิ่งคิดไม่ได้"*
> ไฟล์นี้เปิดไว้ให้เติม ห้ามถือว่าจบแล้ว

## แก่นที่นัทวาง

**สต็อกที่เราตั้ง = คำสั่งงานครัว** ไม่ใช่ตัวเลขในระบบเฉยๆ
ทุกครั้งที่เปิดเมนูสัปดาห์ใหม่ **ต้องกำหนดสต็อกไปเลย** = สั่งครัวไปเลยว่าทำเท่าไหร่

## กฎ

### 1. ตั้งสต็อกตอนเปิดเมนูใหม่ — บังคับ
- อิง **ประวัติยอดขายที่ผ่านมา** ว่าเมนูนั้นขายดีขายไม่ดีแค่ไหน
- **ไม่ต้องห่วงว่าจะเหลือ** — ของเหลือมีทางไปอยู่แล้ว
- แต่ **อย่าให้น่าเกลียดเกินไป**
- 🎯 **เป้าที่นัทเรียกว่า "สวย" = ของหมดพอดีวันศุกร์ หรือวันจันทร์**

### 2. เติมอัตโนมัติ เฉพาะ จันทร์ / อังคาร / พุธ
- **เหตุผลที่จำกัดวัน ไม่ใช่เพราะวันอื่นเติมไม่ได้** — แต่เพราะ **ตอนนี้เรายังคำนวณไม่ได้จริงว่าต้องเติมเท่าไหร่**
- 🔓 **ถ้าแก้เรื่องการคำนวณได้จริงเมื่อไหร่ → เติมวันไหนก็ได้ รวมพฤหัส**
  (ข้อจำกัดนี้เป็นของชั่วคราว ไม่ใช่ของถาวร — อย่าจำผิด)

### 3. เติมเป็นรอบ วันละครั้ง 19:00 น. — ห้ามเติมสุ่มสี่สุ่มห้า
- ❌ **ห้ามเติมตอนครัวกำลังจะเลิกงาน** — นัทยกตัวอย่างของจริง: เติมตอน 15:00 วันที่ 1 ก.ย.
  *"ครัวก็จะงงเลยว่าฉันกำลังจะเลิกงานแล้วต้องมาเติมได้ยังไง"*
- ✅ ประมวลผล **วันละครั้ง ไม่ใช่ตลอดเวลา** — จะได้ประเมินได้ว่า
  ต้องเติมอีกเท่าไหร่ **หรือไม่ควรเติมเลยเพราะจะหมดสัปดาห์แล้ว**

### 4. เติมแล้วต้องแจ้งทุกครั้ง ว่าเติมอะไรเท่าไหร่
เพราะ **การแจ้ง = การสั่งงานครัว** ไม่ใช่แค่รายงานให้นัทรู้

## ทำไม 19:00 ถึงลงตัวพอดี (เหตุผลเชิงกลไก — ผมเช็คแล้ว)
- **18:00 = ปิดรับออเดอร์เมนูสต็อก** -> 19:00 คือ "หลังปิดบัญชีวันนี้ กำลังตั้งเลขของพรุ่งนี้"
- **21:00 = เดดไลน์สั่งวัตถุดิบ** -> เติม 19:00 ยังทันให้ยอดที่สั่งเพิ่มเข้าไปอยู่ในของที่ซื้อคืนนั้น
- ถ้าเลื่อนไปดึกกว่านี้ = หลุดเดดไลน์วัตถุดิบ · ถ้าเช้ากว่านี้ = ไปกวนครัวกลางวัน

## ยังไม่ได้เคาะ (ค้างไว้)
| เรื่อง | ติดตรงไหน |
|---|---|
| เลขตอนเปิดสัปดาห์ใหม่ คำนวณจากอะไรแน่ | รอสูตร — นี่คือตัวปลดล็อกกฎข้อ 2 |
| "ปล่อยข้ามประเทศ" ที่นัทพูด หมายถึงอะไร | ยังไม่ชัด ต้องถามซ้ำก่อนเอาไปใช้ |
| ครัวกับคนกดเปิด ไม่เคยคุยกัน | ครัวรู้กำลังผลิต แต่คนเปิดคือนิว |

## 📕 บทเรียนคืน 1 ก.ย. 2026 (ใบสั่งผลิตที่ถูกถอนทั้งใบ)

**สิ่งที่เกิด:** ผมสั่งผลิต 50 กล่อง → กะปันเบรกไว้ 2 รอบ → นัทสั่งถอนทั้งใบ → **ไม่มีอะไรถึงมือครัวเลยสักข้อความ**

### 1. ⭐ กฎสต็อกที่ถูก — ผมสลับลำดับมาตลอด
```
เป้าหมาย = ให้พอดีสิ้นสัปดาห์
"เหลือดีกว่าขาด" = ทางออกตอนคำนวณพลาด ไม่ใช่เป้าหมาย
```
ผมเอาข้อหลังมาเป็นเป้า เลยกองสต็อกเกินจริง

**สูตร:**
```
ต้องทำเพิ่ม = (ยอดขายต่อวัน × วันที่เหลือถึงสิ้นสัปดาห์) − ของที่มีอยู่แล้ว
                                                          ↑ ต้องหักทุกครั้ง
คำนวณไม่ลงตัว → ปัดขึ้น
```
**ลืมหักของที่มีอยู่ = ผมได้ 48 กล่อง ทั้งที่ของจริงต้องการ 14**

### 2. ตัวเลขยอดขายที่วัดได้ = ค่าต่ำสุด ไม่ใช่ความต้องการจริง
ของหมดทุกวัน -> ยอดขายหยุดที่จำนวนที่มี ไม่ใช่ที่คนอยากได้
**ห้ามตั้งสต็อกจาก "เคยขายได้เท่าไหร่" ตรงๆ** = ตั้งเท่าเดิมตลอดกาล ขาดตลอดกาล

### 3. 🪤 `kitchen_data.updated_at` = คอลัมน์โกหก
upsert ไม่แตะคอลัมน์นี้ · ค้างอยู่ที่ 18 ส.ค. ตลอดกาล ทั้งที่ข้างในอัปเดตทุกวัน
**ความสดของจริงอยู่ที่ field `at` ในแต่ละรายการ** — ตระกูลเดียวกับกับดักประจำบ้าน: เครื่องมือคืนผลลวงโดยไม่มีอะไรแดง

### 4. ห้ามพูดคำว่า "ตอนนี้" โดยไม่เช็คนาฬิกาก่อน
ผมบอกนัทว่า "ตอนนี้บ่าย 3" ตอนที่เป็น 22:30 — หยิบเวลาจากข้อมูลที่อ่านไว้หลายชั่วโมงก่อน
**เครื่องมือไม่ได้พัง (+7 = เวลาไทย ถูกอยู่แล้ว) แต่ผมไม่ได้ดู**

### 5. 🔑 ความเร่งที่มีเหตุผลรองรับ = แรงกดดันให้ข้ามด่านตรวจ (กะปันสรุป)
คืนนี้เหตุผลเร่งฟังดูหนักมาก — ของหมด 5 ตัว · เลยเวลาสั่งวัตถุดิบ · นัทอยากเลิกเป็นคอขวด
**ถ้ากะปันยิงตามที่ผมขอ = ครัวทำของเสียเปล่า 50 กล่อง**

### 6. กติกาถาวรของท่อใบสั่งผลิต (ตกลงกับกะปันแล้ว)
- ใบสั่งทุกใบ **กะปันเทียบกับ `kitchen_data.stock_incoming` ก่อนส่งเสมอ** (ไม่ใช่ `stock_total` — คนละความหมาย) ไม่ตรง = ไม่ส่ง
- **ห้ามส่งใบที่อ้างปุ่ม/หน้าจอที่ยังไม่ verify** — ผมเขียน "ปุ่มเติมเสร็จ" ซึ่งไม่มีจริง
  ของจริง = **`✅ ทำเสร็จแล้ว (N) → ย้ายเข้าของจริง`** ใน `kitchen_queue.html` แท็บตั้งสต็อค → แตะไอคอนดินสอ
- ส่งผ่าน `/api/kapan-say` **ไม่ใช่** `/api/kitchen-console` (ตัวหลังขึ้นชื่อ "นัท" ทั้งที่นัทไม่ได้พิมพ์)

## 📗 บทเรียน 4 ก.ย. 2026 — รอบจัดเมนู 7-13 ก.ย.

### 1. ⭐ กฎเมนูประจำสัปดาห์ (นัทเคาะเอง 4 ก.ย. — ไม่มีข้อยกเว้น)
> *"กฎของเมนูประจำสัปดาห์ คือเราต้องวนเมนูไม่ซ้ำเท่านั้น hook ไว้ **ยังไงก็ต้องได้เมนูใหม่ ถ้าไม่ได้ต้องทวง**"*

**ทวงเมนูใหม่ ไม่ใช่ผ่อนกฎ** · hook = `node scripts/check_weekly_menu.mjs <วันจันทร์>` (05 เขียน · exit 1 ถ้าตก)
⚠️ นิยาม "ซ้ำ" ของด่านตรวจ = **ไม่ถูกขายเลยใน 90 วัน** (เข้มกว่า "ไม่เคยขึ้นเป็นเมนูพิเศษ" ที่ผมใช้ตอนแรก)

### 2. 🔴 เพดานที่คิดว่าเป็นเพดาน มักเป็นแค่ "ข้อมูลอยู่ที่อื่น"
ผมกับ 05 สรุปกันว่า *"คลังมีโภชนาการแค่ 55 เมนู = เพดานอยู่ที่ข้อมูล"* → **นัทค้านทันทีว่าเป็นไปไม่ได้**
ของจริง: **โภชนาการอยู่ในชีทของพลอยมาตลอด** เอาลง DB แล้ว **55 → 175 เมนู**
🎓 **ก่อนประกาศว่า "ทำไม่ได้เพราะไม่มีข้อมูล" ต้องถามเจ้าของก่อนว่ามีที่อื่นไหม** — เราเห็นแค่ DB ไม่ได้แปลว่าโลกมีแค่นั้น

### 3. ✅ ตรวจข้อมูลที่รับมาด้วยฟิสิกส์ ไม่ใช่แค่รูปแบบ
เอาสารอาหารคูณกลับ (P×4 + C×4 + F×9) เทียบกับช่อง kcal → **เจอ 13 แถวเป็นไปไม่ได้**
เช่น `D019 ระบุ 48 kcal แต่สารอาหารรวมได้ 2,443` · ช่องไขมันเป็นเลข 3 หลัก (105-251 ก.) ทั้งที่ปกติ 1-15
**ไม่เดาว่าค่าที่ถูกคืออะไร → ข้ามทั้ง 13 แถว รอพลอยเปิดชีทต้นทาง**

### 4. 💡 ดีมานด์เกาะ "ตำแหน่งในโบรชัวร์" ไม่ได้เกาะ "จาน" (05 คิด)
เมนูใหม่ที่ไม่เคยขึ้น → ไม่มีสถิติรายเมนู **แต่ช่อง S1-S8/D1-D5 มีสถิติ 19-24 สัปดาห์**
→ ตั้งสต็อกจาก **มัธยฐานของช่อง** (ไม่ใช่ค่าเฉลี่ย เพราะ outlier แรง) + 15% ปัดขึ้น
**2 วิธีใช้คนละสถานการณ์:** เมนูเคยขึ้นแล้ว → ใช้สถิติรายเมนู (แม่นกว่า) · เมนูใหม่ → ใช้สถิติรายช่อง (ใช้ได้เสมอ)

### 5. ลำดับ go-live 4 ขั้น — ห้ามสลับ
```
① ถอดชื่อเล่นชุดเก่า  ② ยกชื่อเล่นชุดใหม่  ③ ตั้งสต็อค  ④ เปิดขาย ← ขั้นสุดท้ายเสมอ
```
**เปิดก่อนตั้งสต็อค = ลูกค้าเห็น "หมดแล้ว" ในเสี้ยววินาทีนั้น**
**ตกด่านตรวจ = ไม่เปิดอะไรเลยสักตัว ไม่ใช่เปิดครึ่งเดียว** (เปิดครึ่งเดียวแล้วพัง = ไม่รู้ว่าอยู่สถานะไหน ต้องไล่ย้อนทีละแถว)
**ด่านตรวจต้องรันซ้ำ ณ วินาทีที่กด** — ของขยับได้เสมอระหว่างที่คุยกันอยู่
