Meal Plan ของ Under360 **ไม่ใช่ fixed set** — ยืดหยุ่นรายลูกค้า:

- **ข้อจำกัดรายคน:** ลูกค้าระบุได้ (ไม่กินเนื้อวัว/ผักชี/อาหารเกาหลี ฯลฯ) → ระบบ/แอดมินไม่ยัดเมนูนั้นให้
- **Weekly request menu:** ทุกสัปดาห์ใส่เมนูให้ลูกค้าเลือกเปลี่ยนได้ 2-3 รายการ (กันเบื่อ)
- **ดุลยพินิจแอดมิน:** หลังบ้านตัดเมนูที่ลูกค้าไม่เอาออก → สลับเป็น HP/LC เมนูอื่นเฉพาะคนนั้น
- **ห้ามซ้ำ request (สำคัญ):** ลูกค้าขอเมนูเดิมเบิ้ลหลายกล่องไม่ได้ เช่น แซลมอน 7 กล่อง = ขาดทุน → ต้องมี guard กันซ้ำ + กันต้นทุนเกิน

**กฎ 3:4 (cost balance — หลังบ้าน ไม่บอกลูกค้า):**
- เมนูต้นทุนสูง (แซลมอน/กระพง/กุ้ง) → ใส่ **3 กล่อง (ไม่เกิน 4)**
- เมนูต้นทุนต่ำ (หมู/ไก่/เนื้อ) → **4 กล่อง**
- อัตราส่วน **3:4 ตลอด** → เซ็ต 7 / 21 / 84 กล่อง หารลงตัว 3:4 พอดี (7=3+4, 21=9+12, 84=36+48)
- น้องนิวต้อง compose เมนูให้คุมต้นทุนตามสัดส่วนนี้

**Meal Plan picker (LIFF s-meal-plan) — ที่อยากให้เป็น version นี้:**
- สเต็ป 1 เลือก HP/LC → ใส่**ข้อความอธิบายจุดเด่น**ของแต่ละแพคคร่าวๆ
- สเต็ป 2 เลือกขนาด (7/21/84) — มีแล้ว
- สเต็ป 3 **Request menu = แอดมิน assign ไม่ใช่ช่องพิมพ์อิสระ** → โชว์เมนูที่แอดมินกำหนดให้เลือก (~3 ช่อง, แอดมินคลิกเพิ่มจากลิสต์เมนูใน DB) · ตอนนี้ของจริงเป็น free-text input → ต้องเปลี่ยน · mock Request A/B ไปก่อนได้
- **ข้อจำกัดลูกค้า (ไม่ชอบทานอะไร):** ให้เลือกอีกบรรทัดในรายละเอียดลูกค้า
- ราคา MP_SETS ยัง mock — ใส่จริงทีหลัง (นัทบอก workflow สำคัญกว่าราคา)

**Why:** เป็น core business logic ที่ไม่อยู่ในโค้ด — กระทบดีไซน์ระบบ assign เมนู (น้องนิว) โดยตรง
**How to apply:** งานนี้คือ **น้องนิว v0.4** (assign 7 เมนู/คน/สัปดาห์ + request ≤2-3 + กันซ้ำ + กันขาดทุน) ไม่ใช่ card link ธรรมดาในตอนนี้ การ์ด `__meal_plan__` ปัจจุบันเป็นแค่ placeholder เปิด picker HP/LC ทั่วไป เกี่ยว [[response-style-concise]]

## ✅ Schedule engine สร้างแล้ว (commit a0f542c) — สถานะล่าสุด

ตาราง **`mp_deliveries`** = แกนกลางใหม่ (1 แถว = 1 รอบส่ง 7 กล่อง) แทนที่จะ manual แอดมินเองทั้งหมด:
- **รอบส่ง = boxes/7** (trial=1, weekly=3, monthly=12 รอบ) ส่งเฉพาะ **จันทร์/พุธ/ศุกร์** เท่านั้น — auto-gen ตอน submitOrder() สำเร็จ (`generateMpDeliveries()` ใน liff_customer.html)
- **Request window** เปิดอัตโนมัติ 3 วันก่อนส่ง (`request_opens_at` = delivery_date-3, `request_deadline` = delivery_date-1)
- **status enum** (ใช้เหมือนกันทุกไฟล์ — ห้ามเพิ่ม/เปลี่ยนโดยไม่ sync ทุกจุด): `scheduled → request_open → (request_submitted | no_change) → menu_assigned`, หรือ `skip_requested → skipped`, จบด้วย `delivered`/`cancelled`
- **ระบบเป็นฝ่ายเริ่มเสมอ ไม่รอลูกค้า** — cron เช็คทุกวัน ถึงเวลาไหนก็ push หาลูกค้าเอง ลูกค้าไม่ต้องทำอะไรก่อน
- **Auto-close ถ้าลูกค้าไม่ตอบ (ปรับแล้ว commit dd1d550):** ถ้าเลย `request_deadline` เวลา **18:00** (ค่าคงที่ `MP_REQUEST_DEADLINE_HOUR` ใน liff_customer.html — ใช้เวลาเดียวกับ CUTOFF_HOUR ของออเดอร์ปกติ) → ระบบปิดอัตโนมัติเป็น `no_change` **เงียบๆ ไม่ push LINE แล้ว** (กันสแปมลูกค้า) — ลูกค้าเห็นแค่เวลานับถอยหลัง "⏳ เหลือเวลาปรับเมนูรีเควส" ในหน้า `s-mp-manage` ล่วงหน้าแทน (คำนวณฝั่ง client จาก request_deadline+18:00 ไม่ต้องรอ cron อัพเดท status ก็ขึ้น "หมดเวลาแล้ว" ถูกต้องทันที) — cron ยังปิด status ฝั่ง DB เหมือนเดิมกันแอดมิน/ครัวค้าง แค่ตัด push ออก
- **เตือนก่อนส่ง 1 วัน** — แยกจาก request logic คนละเรื่อง ใช้คอลัมน์ `day_before_notified_at` (ไม่ใช่ `notified_at`) เช็คจาก `delivery_date=พรุ่งนี้` ไม่สนสถานะ request เลย (ยกเว้น skipped/cancelled)
- **LIFF** — หน้า `s-mp-manage` (เข้าจาก s-orders banner หรือ deep link `?screen=mp-manage`) ให้ลูกค้าเลือก request เมนูเอง (ตอน status=request_open) — **ไม่ต้องทักแอดมินแมนนวลแล้ว**
- **ย้ายวันส่งเอง (commit f1f9571 — ปรับล่าสุด):** ลูกค้ากด "📅 ขอเลื่อน/ย้ายวันส่ง" เลือกวันใหม่ (จ/พ/ศ เท่านั้น กันชนวันที่รอบอื่นในแพลนเดียวกัน) → self-service ทันที ไม่ต้องรอแอดมิน — update delivery_date + recompute request_opens_at/deadline + reset status='scheduled' **+ เคลียร์ menu_items/customer_request เป็น [] ด้วย** (เมนูเดิมไม่เกี่ยวกับวันใหม่ ปล่อยว่างให้ assign ใหม่) — **แยกจาก** "❌ ยกเลิกรอบนี้เลย (ไม่ย้ายวัน)" (เดิมชื่อ "ข้ามรอบนี้") ซึ่งยังต้องให้แอดมิน approve เหมือนเดิม เพราะกระทบจำนวนกล่องที่ต้องส่งจริง/เงิน — สอง action นี้แยกกันชัดเจนแล้ว ไม่ใช่ปุ่มเดียวกำกวมแบบเดิม
- **OH** — แท็บแพลนเมนู มีส่วน "Meal Plan ระยะยาว" เห็นคิวยาว แก้วันที่/สถานะ/assign เมนูต่อรอบ (จาก MENU_POOL) ไฮไลต์แถว request_submitted/skip_requested ที่ต้องดำเนินการ (`no_change` ไม่ถือเป็นแถวต้องดำเนินการ)
- **OH แท็บแพลนเมนู (commit afa6ca4) — เลิก mock แล้ว:** แถว = ลูกค้าจริงจาก mp_deliveries, คลิกชื่อลูกค้า=เลือกทั้งแถว คลิกช่องรอบ=เลือกรอบเดียว แล้วกดเมนูฝั่งซ้าย assign พร้อมกันหลายช่องได้ บันทึกตรงเข้า `mp_deliveries.menu_items`
- **✅ คอลัมน์ = วันที่จริง ไม่ใช่ round index (commit 2f19ec5 — ปรับล่าสุด):** เดิม column คือ "รอบ 1/2/3.." ของแต่ละแพลนเอง (แพลนเริ่มคนละวันก็เลยไม่ตรงแนวกัน) เปลี่ยนเป็น union วันที่จัดส่งจริงของทุกแพลน เรียงตามปฏิทินจริง — วันที่ 6 ก.ค. ของทุกคนจะอยู่คอลัมน์เดียวกันเป๊ะไม่ว่าจะเป็นรอบที่เท่าไหร่ของใคร ช่องที่ไม่มีรอบวันนั้นโชว์ "—" ในเซลล์ยังโชว์ "รอบ N" กำกับไว้ (ไม่ใช่วันที่ซ้ำกับ header)
- **✅ ปุ่ม "เลือกทั้งคอลัมน์ type เดียวกัน" ทำแล้ว (commit c32f452, ผูกกับวันที่แล้วใน 2f19ec5):** header แต่ละคอลัมน์วันที่มีชิป "⚡LC ทั้งคอลัมน์"/"⚡HP ทั้งคอลัมน์" คลิกเดียวเลือกลูกค้าทุกคน type นั้นที่มีรอบวันนั้นพร้อมกัน (โชว์เฉพาะคอลัมน์ที่มีลูกค้า type นั้นจริง) ตรงกับ workflow shared-lineup ข้างบนพอดี — ทดสอบผ่าน preview แล้วทั้งคู่ (bulk-assign เข้าเฉพาะ type ที่เลือกจริง, alignment ข้ามแพลนคนละวันเริ่มถูกต้อง)
- **KQ** — section แยกอ่านจาก mp_deliveries ตามวันที่เลือกดู มีปุ่มมาร์คส่งแล้ว
- **LINE push อัตโนมัติ** — `api/notify-mp-requests.js` (endpoint เดียว 3 jobs ต่อรัน: เปิด request window / auto-close no_change / เตือนก่อนส่ง 1 วัน) + `vercel.json` cron (ทุกวัน 08:00 ไทย)
- **DB (main_database_v2.html) "🍳 ผลิตวันนี้" (commit `12299a4`, เดิมเป็น mock sub-view "กำหนดเมนูลูกค้า"):** ให้ครัวดู mp_deliveries ของวันนั้นโดยไม่ต้องสลับไป OH/KQ — สรุปยอด (รอบ/HP/LC/รีเควสเอง/ยังไม่ครบ) + aggregate เมนูที่ต้องผลิตกลุ่มตาม code พร้อมช่องโน้ตเปลี่ยนเมนูฉุกเฉินรายคน (ผูก `menu_items[].note` ตัวเดียวกับที่ OH ใช้ set/แก้อยู่แล้ว ไม่ใช่ข้อมูลแยกชุด — พิมพ์จาก DB เห็นที่ OH ด้วย)
- **⚠️ ยังไม่แก้ (พบ 2026-07-04, ไม่กระทบการใช้งาน):** `mpIsoDate()` ในแท็บ "แผนผลิต" (main_database_v2.html, คนละเรื่องกับ mp_deliveries — เป็นกริดวางแผนผลิตรวมผูก `daily_menu_assignments`) ยังใช้ `.toISOString().split('T')[0]` แบบเดียวกับบั๊ก timezone ข้างบนเป๊ะ แต่ยังไม่มีรายงานปัญหาจริงจึงยังไม่แตะ — เจอโค้ดนี้เมื่อไหร่ให้แก้ด้วย pattern เดียวกัน

**🐛 บั๊กร้ายแรงที่แก้แล้ว (พบระหว่างเทส commit afa6ca4):** `d.toISOString().slice(0,10)` แปลงเป็น UTC ก่อนตัด — เที่ยงคืนเวลาไทย (UTC+7) = 17:00 UTC เมื่อวาน ทำให้ทุกวันที่ที่คำนวณจาก local Date object ผิดไป 1 วันเสมอ (โดยเฉพาะ `generateMpDeliveries` ที่ตั้งเวลาเที่ยงคืนตรงๆ — ทำให้รอบส่งตกวัน อา/อ/พฤ แทนที่จะเป็น จ/พ/ศ ทุกครั้ง 100%) แก้โดยเพิ่ม `localYMD()`/`toISO()` แบบ getFullYear/getMonth/getDate (ค่าท้องถิ่นเสมอ ไม่ผ่าน UTC) — **กฎจำไว้: ห้ามใช้ `.toISOString().slice(0,10)` หรือ `.split('T')[0]` กับวันที่ท้องถิ่นเด็ดขาด ใช้ได้เฉพาะกับ timestamp/created_at/updated_at ที่ตั้งใจให้เป็น UTC จริงๆ เท่านั้น** — เจอ pattern นี้ซ้ำใน 3 ไฟล์ (liff_customer/operation_hub/kitchen_queue) แก้ครบแล้วทุกจุด

**🗒️ Business logic สำคัญที่นัทอธิบาย (2026-07-02) — เมนูแต่ละรอบเป็นแบบ shared lineup ไม่ใช่ custom รายคนจากศูนย์:**
ทุกรอบ ลูกค้าที่ไม่ได้ request อะไรพิเศษ (คนส่วนใหญ่) จะได้ **เมนู 7 กล่องชุดเดียวกันหมด** ภายในประเภทเดียวกัน (LC ทุกคนได้ชุดเดียวกัน, HP ทุกคนได้ชุดเดียวกัน) — ไม่ใช่แอดมิน/น้องนิว compose ทีละคนจากศูนย์ทุกรอบ
- ข้อแตกต่างต่อคนเกิดจาก 2 ทางเท่านั้น: (1) ลูกค้า request เอง (มีอยู่แล้ว) (2) **แอดมิน/AI agent สังเกตเองว่าลูกค้าคนไหนได้เมนูเดิมซ้ำบ่อยเกินไป (เบื่อ) แล้วโยกสลับให้ 1-2 เมนู** เป็นดุลยพินิจเชิงรุก ไม่ใช่ลูกค้าขอ
- **ผลต่อดีไซน์ OH grid:** การ workflow ที่มีประสิทธิภาพคือ "ตั้งชุดมาตรฐานของรอบนั้นให้ทุกคน (type เดียวกัน) พร้อมกันทีเดียว" แล้วค่อยแก้เฉพาะคนที่ต้อง deviate — ตอนนี้ grid รองรับผ่าน multi-select (เลือกหลายช่อง/หลายลูกค้าแล้ว assign พร้อมกัน) แต่ยังไม่มีปุ่ม "เลือกทุกคนที่เป็น LC ในรอบที่ N" แบบ 1 คลิก (ยังต้องเลือกทีละคน/ทีละช่องเอง) — เป็น follow-up ที่มีประโยชน์ถ้าจำนวนลูกค้าเยอะขึ้น (ยังไม่ได้ทำ)
