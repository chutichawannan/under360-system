## ❶ หน้าตาข้อมูล — 1 การ์ด = 1 เมนู

สคริปต์คืน JSON 2 กอง (`--json`) — **การ์ดต้องรองรับทั้งคู่ ไม่ใช่แค่กองแรก**

### กอง `cards[]` — เฝ้าได้จริง (มีทั้งเลขผลิตและเลขเหลือ)
```jsonc
{
  "code": "A13", "name": "แฮมเบิร์กหมูผสมไก่ซอสบาบีคิว",
  "level": "risk",          // risk = จะเหลือ ≥30% | watch = 15-30% | ok = ปกติ
  "produced": 6,            // ผลิต (actual_stock)
  "sold": 0,                // ขายสัปดาห์นี้ (order_items)
  "left": 4,                // เหลือ (stock_total)
  "daysLeft": 4,            // เหลือกี่วันในสัปดาห์
  "sellThroughPct": 0,      // ขายไปกี่ % ของที่ผลิต
  "targetPct": 43,          // เป้าที่ควรขายได้ ณ วันนี้ (= วันที่/7)
  "projectedLeft": 6,       // คาดจบสัปดาห์เหลือกี่กล่อง  ← ตัวเลขที่ทำให้ต้องรีบ
  "suggestNextWeek": 5,     // งาน ก: รอบหน้าควรผลิต
  "actions": ["ดันขึ้นหน้าแรก LIFF", "แถมกับออเดอร์อื่น", "ลดราคาเคลียร์"]
}
```

### กอง `blockers[]` — **ยังเฝ้าไม่ได้ (ตอนนี้ 21/22 อยู่กองนี้)**
```jsonc
{
  "code": "A1", "name": "อกไก่คั่วพริกเกลือ",
  "reason": "ยังไม่มีใครกรอก \"ผลิตได้จริง\" ใน KQ (actual_stock = 0)",
  "soldThisWeek": 0,
  "histAvgPerWeek": 2,      // median สัปดาห์ที่ขายจริง
  "suggestNextWeek": 3,     // ✅ งาน ก ใช้ได้แม้ยังไม่มีเลขผลิต
  "histNote": "ขายจริง 6 สัปดาห์ (จากย้อนหลัง 8) · 06-08=1 · 06-15=2 · ..."
}
```

> ⚠️ **อย่าซ่อน `blockers` เพราะดู "ไม่สวย"** — ตอนนี้มันคือ **สถานะจริงของร้าน 21/22 เมนู** ถ้าซ่อน = นัทเห็น dashboard ว่างแล้วนึกว่าไม่มีปัญหา
> เสนอ: การ์ด blocker หน้าตาต่างจาก risk (สีเทา/ขอบประ) + เขียนตรงๆ ว่า **"ต้องทำอะไรถึงจะเฝ้าได้"** — นี่คือ CTA ที่ทำให้ครัวเริ่มกรอกจริง

### `reason` มี 3 แบบ (ขึ้นข้อความต่างกัน)
| แบบ | แปลว่า | ทางแก้ |
|---|---|---|
| `stock_total = null` | เมนูตั้ง "ไม่จำกัด" → ลูกค้าสั่งไม่ตัดสต็อก | ตั้งเลขในแท็บ **"ตั้งสต็อค"** ของ KQ ก่อน 1 ครั้ง |
| `actual_stock = 0` | ยังไม่มีใครกรอก "ผลิตได้จริง" | ครัวกรอกใน KQ |
| `ข้อมูลขัดกัน` | เหลือ > ผลิต (A13: ผลิต 6 · stock 9) | กรอก "ผลิตได้จริง" รอบใหม่ให้ตรง |

## ❷ สคริปต์คืนค่ายังไง → **เสนอ: ไม่ต้องสร้างตาราง ไม่ต้องตั้ง cron**

CC เสนอเขียนลง `niw_alerts` แล้ว dashboard อ่าน — **ผมเสนอทางที่เบากว่าสำหรับ v1:**

> **ให้ `command_center.html` คำนวณเอง client-side** (ยก algorithm จากสคริปต์ไปเป็น JS ในหน้า)

**ทำได้เพราะ:** logic ทั้งหมด = query Supabase + เลขคณิต ไม่มีอะไรที่ต้องใช้ node
- ✅ ไม่ต้องสร้างตารางใหม่ · ไม่ต้อง cron · ไม่ต้อง service key
- ✅ **ตัวเลขสดเสมอ** (ครัวกรอกปุ๊บ รีเฟรชเห็นปั๊บ) — ถ้าใช้ตาราง+cron จะช้าไป 1 รอบ ซึ่งขัดกับงานที่ต้องรีบ
- ✅ ตรงคอนเวนชัน repo (single-file HTML + Supabase ตรง)
- ⚠️ แลกกับ: logic อยู่ 2 ที่ (สคริปต์ + หน้าเว็บ) → กันด้วยการให้ `weekly_special_watch.mjs` เป็น **ตัวอ้างอิงจริง** ถ้าแก้สูตรต้องแก้ทั้งคู่ (จดหมายเหตุไว้ในทั้ง 2 ไฟล์)

**เมื่อไหร่ค่อยขยับไป `niw_alerts`:** เมื่อต้องการ ① ประวัติว่าเคยเตือนอะไรไปบ้าง ② ส่ง LINE/notification ③ วัดว่าเตือนแล้วแอดมินทำอะไร — **v1 ยังไม่ต้อง**

**ผมพร้อมส่งฟังก์ชัน JS สำเร็จรูปให้ CC แปะ** (พารามิเตอร์เดียว: `sb` client · คืน `{cards, blockers}` เหมือน JSON ข้างบน) — บอกมาแล้วผมเขียนให้

## ❸ ความถี่ — **คำนวณตอนเปิดหน้า/กดรีเฟรช** (client-side ไม่มีต้นทุน)
- query ที่ใช้: `menu_items` (1 ครั้ง) + `order_items` ช่วง 9 สัปดาห์ของเมนูที่เฝ้า (~ไม่กี่ร้อยแถว) = เบามาก
- ถ้าอยากประหยัดกว่านี้: cache ใน memory 5 นาที
- ⏰ **ยึดเวลาไทย (Asia/Bangkok) เสมอ** — สัปดาห์ = จันทร์→อาทิตย์ · นัทอยู่ PST ถ้าคำนวณจากเครื่องจะเพี้ยนไป 1 วัน

## 📌 หมายเหตุที่ต้องรู้ก่อนต่อการ์ด
1. **flag `is_weekly_special` ยังไม่นิ่ง** (U จะเปลี่ยนเป็นระบบแท็ก · รอนัทเคาะ) → สคริปต์รับ `--stocked` เป็นทางเลี่ยง (เฝ้าทุกเมนูที่ตั้งสต็อก) · การ์ดควรรองรับสลับโหมดได้
2. **ตอนนี้ `cards` = ว่าง · `blockers` = 21** → ถ้า CC ต่อการ์ดแล้วเห็นหน้าว่าง **นั่นคือถูกต้อง ไม่ใช่บั๊ก**
3. **งาน ก (suggestNextWeek) ใช้ได้ทุกเมนูอยู่แล้ว** แม้อยู่ในกอง blockers → **การ์ดควรโชว์ตัวเลขนี้ตั้งแต่วันนี้** ไม่ต้องรอครัว
